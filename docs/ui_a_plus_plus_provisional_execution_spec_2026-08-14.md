## 1. 方案结论

### 1.1 产品定位

面向用户的价值表达：

> **把患者说的话，变成可确认、可交接、可回看的随访记录，而不替医护人员下判断。**

首页/演示主文案：

> **患者说的话，一路跟到复诊速览。**

对外阶段说明：

> ContinuCare 当前是只使用合成数据的连续照护产品原型；下一阶段建议寻找设计合作方，不应称为临床试点或已部署医疗系统。

### 1.2 核心体验亮点

唯一主亮点是 **“原话接力”**：

- 患者先确认系统是否准确理解自己的表达；
- 护士看到同一段患者确认内容，并完成例行记录核对；
- 医生先看到患者事实、护理动作和“尚未评估”的边界；
- 审核者能解释每一步发生了什么、为什么完成或停止；
- 每条被交接的内容，都能在当前位置一跳回到来源；
- 医生可以调整速览措辞，但来源关系不随措辞改变。

“原话锚点”是内部设计术语，不直接对患者使用“证据、取证、存证、核验”等法律化或工程化说法。

### 1.3 A++ 的一句话设计规则

> **默认只显示做出正确动作所需的最小事实；来源一跳可达；边界与后果永不折叠。**

这里的“最小”不是把内容删掉，而是按角色安排查看顺序：

- 先看当前任务；
- 需要判断时查看来源；
- 调查异常时查看完整记录；
- 任何角色都能找到进一步信息入口；
- 但不能让所有角色一上来面对同一堆技术信息。

### 1.4 当前推荐方向

推荐并暂定执行的方向是：

> **A++「原话接力」：患者移动优先、医护桌面优先、审核解释优先、演示者独立导览。**

它吸收原方案 B 的记录连续性、来源关系和排版秩序，但不采用文书拟物、并排版本 diff、大型时间线或高密度“证据墙”。

## 2. 不能被 UI 改写的事实边界

以下内容必须在实施、文案、概念图和演示中保持真实：

1. 只使用合成患者和合成运行数据；
2. clinical assessment 始终为 `not_assessed`；
3. 没有自动诊断、风险分级、治疗建议或用药建议；
4. 当前没有获批 ClinicalRule，也没有真实 Alert；
5. Communication 不会实际发送；
6. `SEND_ENABLED=False`；
7. 飞书和 Aily 为 Mock，Bitable disabled；
8. 没有真实租户验证、真实外部调用或真实数据写入；
9. Knowledge 独立只读，不参与患者故事、Task、Summary 或完成判定；
10. `candidate_unsure` 不是终态，患者仍可接受或拒绝现有候选；
11. 全部候选拒绝后本轮结束，当前不支持同一轮立即重新表述；
12. Task 的 rejected、cancelled、failed、entered-in-error 都会停止后续业务动作；
13. `story_complete` 只表示合成演示 9/9 完成，不代表产生临床结论；
14. 明确重新开始会替换整份本地合成 Demo 运行数据，包括本轮追溯记录；
15. 页面加载、刷新、查看来源、展开详情和浏览 Knowledge 都不应产生业务写入；
16. 当前没有真实身份认证和角色权限系统；界面中的角色切换只用于合成演示；
17. 不得新增或暗示“联系医生”、真实发送、风险警报、EMR 写回或诊疗能力。

### 2.1 全局固定边界文案

患者端：

> 确认的是您说的话有没有记对，不是确认诊断。本演示不会发送消息。

护士端：

> 这里核对的是患者记录，不判断风险，也不提供诊疗建议。

医生端：

> 尚未提供临床评估。以下内容只整理已确认记录与护理动作。

演示者/审核端：

> 合成数据 · 无临床评估 · 无风险分级 · 无真实发送 · 外部系统为 Mock/disabled。

模拟外部动作必须就地标明：

> 模拟（未真实发送 / 未写入）

不能只在页面底部统一放一条免责声明，避免用户在具体动作处产生错误理解。

## 3. “六页”到底是什么意思

当前代码中共有六个可访问界面：一个入口页和五个功能页。

| 代码入口 | 现有职责 | A++ 面向用户的名称 | 主要使用者 |
|---|---|---|---|
| `app.py` | Demo 首页、开始/重置、全局进度 | 合成演示导览 | 演示者 |
| `pages/1_patient_followup.py` | 患者输入、候选确认、问卷 | 我的随访 | 患者 |
| `pages/2_nurse_risk_center.py` | manual-review Task 与旧 Alert 区域 | 护士工作台 | 护士 |
| `pages/3_doctor_summary.py` | 确定性 Summary 与 DoctorReview | 复诊速览 | 医生 |
| `pages/4_audit_log.py` | AuditEvent 和技术追溯 | 记录追溯 | 审核者 |
| `pages/5_knowledge_evidence.py` | 独立只读 Knowledge | Knowledge 资料库 / 症状采集参考 | 医护资料查询者 |

“保留六页”只表示保留六种功能界面，**不表示把六个入口同时展示给每个用户**。

### 3.1 目标产品空间

```text
患者空间
└── 我的随访

医护工作空间
├── 护士工作台
└── 复诊速览

保障空间
└── 记录追溯

独立资料空间
└── Knowledge 资料库

演示者元界面
└── 合成演示导览（跨角色线性演示，不是假装成真实权限系统）
```

### 3.2 角色导航规则

| 角色 | 默认导航 | 不默认出现 | 进一步查看入口 |
|---|---|---|---|
| 患者 | 仅“我的随访” | 护士、医生、审计、Knowledge、技术状态 | “这个选择会怎样影响本轮”“查看这一轮记录” |
| 护士 | “待处理 / 已处理” | 医生摘要、审计日志、Alert 指标墙 | “查看患者原话”“查看之前的任务动作”“查看完整接力记录” |
| 医生 | “复诊速览” | 护士队列、患者表单、技术审计表 | “查看患者原话”“查看护理动作详情”“查看完整接力记录” |
| 审核者 | “记录追溯” | 业务操作按钮 | “为什么在这里停止”“查看资源关系”“查看技术详情” |
| Knowledge 使用者 | 主题列表和资料详情 | 患者上下文、故事进度、业务动作 | “查看来源与版本”“查看适用范围” |
| 演示者 | 五步线性导览 | 六张等权入口卡片 | 角色切换、负向路径、演示数据管理 |

### 3.3 演示者的五步导览与六个页面的关系

演示故事使用五个叙事步骤：

```text
1 患者表达 → 2 患者确认 → 3 护士核对 → 4 医生速览 → 5 记录追溯
```

- 第 1、2 步都发生在“我的随访”页；
- “合成演示导览”是元界面，不是故事中的业务角色；
- Knowledge 是独立资料库，不参与五步故事；
- 因此六个代码页面与五个故事步骤并不矛盾。

## 4. 按角色渐进披露模型

### 4.1 四层信息结构

| 层级 | 内容 | 是否可收起 |
|---|---|---|
| L0 边界与后果 | 会改变用户决定的后果、未评估、未发送、终态停止 | **不可收起** |
| L1 当前任务 | 做正确动作所需的最小事实、当前状态、下一步 | 默认显示 |
| L2 判断依据 | 原话、上一动作、来源关系、版本说明 | 一跳展开 |
| L3 完整记录 | 资源 ID、版本、Provenance、AuditEvent、原始 JSON | 默认隐藏，仅按需展开 |

同一事实在同一屏最多提供一个主要展开入口，避免“查看详情 / 查看来源 / 查看记录”三处重复指向相同内容。

### 4.2 每个角色默认看什么

| 角色 | 默认可见 | 按需展开 | 不应出现在第一屏 |
|---|---|---|---|
| 患者 | 原话、系统记法、三种决定、决定后果、非诊断边界、急救提示 | 本轮影响、提交记录 | FHIR、模型模式、candidate、Task、Provenance |
| 护士 | 队列、任务类型、提交时间、患者确认表达、当前动作、非风险边界 | 患者原话、先前动作、完整接力记录 | Alert 数量、获批规则指标、SLA 紧急色、JSON |
| 医生 | 患者事实、护理动作、未评估边界、当前速览、措辞决定 | 原话、上一版措辞、护理详情、完整记录 | 技术计数器、发送能力指标、并排 diff |
| 审核者 | 当前结论、直接原因、已产生/未产生、参与者动作与时间 | 资源关系、版本、技术详情 | 默认 JSON 表、英文事件名、装饰性进度动画 |
| Knowledge | 主题、支持范围、不支持范围、固定独立性说明 | 来源、版本、scope、历史资料 | 患者姓名、故事状态、患者上下文 |
| 演示者 | 当前角色、五步导览、当前边界、正负路径 | 集成状态、重置影响、技术 fixture | 六块角色 Dashboard、虚构指标 |

## 5. 跨角色核心旅程

### 5.1 60 秒正向演示

1. 演示者在“合成演示导览”看到当前故事状态和下一步；
2. 患者页显示原话“我今天拉肚子。”与系统记法“今天有腹泻”；
3. 患者选择“对，就是这个意思”，明确知道自己不是在确认诊断；
4. 护士工作台出现一条“例行记录核对”，按提交时间进入队列；
5. 护士接手、开始核对并记录受控结果；
6. 系统产生中性沟通文字，页面明确“模拟，未真实发送”；
7. 医生看到三项分开的信息：患者确认的表述、护理动作、尚未提供临床评估；
8. 医生在适用的非终态 Summary 版本上保留、调整或不采用当前措辞；
9. 沟通文字经护士人工核对，医生按当前来源生成/刷新 ready 速览；
10. `story_complete` 后所有角色页只读，审核页解释 9/9 已完成但没有临床结论或真实发送。

说明：DoctorReview 是已实现的版本决定能力，但不等于临床签署，也不是 9/9 完成判定的同义词。若在非终态 pending Summary 上作出决定，来源变化后生成的新版本不会继承旧决定。`story_complete` 后不再提供新的业务动作。

### 5.2 20 秒负向演示

```text
患者全部拒绝
→ 本轮结束
→ 不生成患者确认记录、护士任务或医生速览
→ 审核者看到“为什么停止、已经产生、没有产生”
→ 本轮不能立即重新表述
```

### 5.3 “不太确定”路径

```text
患者选择“不太确定”
→ 页面保留当前候选
→ 不创建 QR、Observation 或护士任务
→ 患者仍可选择“对，就是这个意思”或“不是这个意思”
```

`candidate_unsure` 不能被设计成灰掉所有按钮的等待状态，也不能由护士或医生代替患者决定。

## 6. 全局状态语言与动作

### 6.1 主流程状态

| 内部状态 | 面向用户的标题 | 当前角色 | 主动作/下一步 | 必须同屏出现的边界 |
|---|---|---|---|---|
| `not_started` | 这次合成演示还没有开始 | 演示者 | 开始一轮合成演示 | 开始会准备未确认内容，不替任何角色作决定 |
| `candidate_ready` | 请确认我们记得是否准确 | 患者 | 选择三种决定之一 | 不是确认诊断；全部拒绝会结束本轮 |
| `candidate_unsure` | 这段记录还没有确认 | 患者 | 仍可接受或拒绝 | 尚未形成患者确认记录或护士任务 |
| `candidate_rejected` | 本轮已结束：没有形成确认记录 | 患者/审核者 | 查看这一轮记录 | 本轮不能立即重新表述 |
| `patient_confirmed` | 患者已确认这段表述 | 系统过渡 | 等待例行记录核对 | 临床评估仍未进行 |
| `task_requested` | 等待护士接手 | 护士 | 接手这项核对 | 例行记录核对，不是风险警报 |
| `nurse_received` | 护士已接手 | 护士 | 开始核对 | 只核对记录，不判断风险 |
| `nurse_in_progress` | 正在核对这项记录 | 护士 | 记录受控结果 | 不生成诊断或治疗建议 |
| `communication_pending` | 核对结果已记录，沟通文字尚待确认 | 医生 | 按当前记录生成 pending 速览 | 文字未发送；查看页面不会自动生成 |
| `doctor_brief_pending` | 当前速览已生成，沟通文字仍待核对 | 医生/护士 | 返回护士端核对文字 | pending 不等于发送或临床结论 |
| `communication_ready` | 沟通文字已核对 | 医生 | 按当前记录生成/刷新速览 | 本演示不会发送 |
| `story_complete` | 演示记录链已走完 | 审核者 | 查看完整记录 | 9/9 不代表临床结论；没有真实发送 |

`doctor_brief_ready` 是底层 9/9 里程碑，不是 `read_competition_demo()` 会单独投影给用户停留的页面阶段；当前 ready Communication 被最新速览精确引用后，整体直接投影为 `story_complete`。

### 6.2 异常终态

| 内部状态 | 主标题 | 解释 | 后续 |
|---|---|---|---|
| `task_rejected` | 流程已停止：护士未接受这项核对 | 保留拒绝动作和已存在记录；不产生后续沟通文字或医生速览 | 只读查看记录 |
| `task_cancelled` | 流程已停止：这项核对已取消 | 保留取消前记录；不继续后续业务动作 | 只读查看记录 |
| `task_failed` | 任务没有完成，后续流程已停止 | 显示已记录的失败原因；没有原因则显示“原因：未记录” | 只读查看记录 |
| `task_entered_in_error` | 记录错误：任务已标记为不应存在 | 历史记录保留并标明状态；该 Task 不再被当作有效业务记录 | 只读查看记录 |

### 6.3 三类终态模板

所有终态共享一套内容字段，但不使用一模一样的视觉模板。

#### A. 正常完成

- 中性深青色标题；
- 标题：`演示记录链已走完`；
- 原因：`合成演示 9/9 完成`；
- 不使用庆祝动画、绿色对勾墙或“临床成功”。

#### B. 业务停止

- 琥珀色提示；
- 标题从具体动作得出，例如 `本轮已结束：患者没有确认这段记录`；
- 明确已经产生、没有产生和为何不能继续。

#### C. 记录错误

- 红色边界；
- 标题明确是记录有效性问题，不包装为普通取消；
- 对 entered-in-error 使用 `原因：未记录` 作为缺失字段，不编造一段似乎真实的原因描述。

三类都包含：

1. 人能读懂的结论；
2. 已记录的原因，缺失时明确写 `原因：未记录`；
3. 已经产生；
4. 没有产生；
5. 查看完整记录；
6. 固定能力边界。

## 7. 六个界面的详细规格

## 7.1 合成演示导览（`app.py`）

### 页面职责

给演示者控制和讲解合成故事，不作为患者、护士或医生的真实首页。

### 第一屏结构

1. 左上：`ContinuCare｜合成演示导航`；
2. 邻近说明：`角色切换仅用于演示，不代表已实现身份认证或权限控制。`；
3. 固定能力边界：`不提供临床评估、诊断或风险分级；不会真实发送；外部系统为 Mock。`；
4. 五步线性导览：患者表达 → 患者确认 → 护士核对 → 医生速览 → 记录追溯；
5. 当前步骤用一个实心节点和文字标识，其他步骤不用多色状态；
6. 当前角色内容预览；
7. 右侧/下方说明“这一分钟证明什么”和“不声称什么”；
8. 负向路径作为一条可展开的 20 秒演示带。

### 默认显示

- 当前演示角色；
- 当前步骤；
- 上一步已经发生什么；
- 下一步要去哪里；
- 三条固定边界；
- 当前故事是进行中、已停止还是已完成。

### 默认收起

- 外部适配器详细状态；
- 资源数量；
- 旧技术 fixtures；
- 本地数据库标识；
- 重新开始/替换数据功能。

### 重新开始的交互

重新开始只放在 `管理本地演示数据` 的独立展开区，不放在主操作旁边。

第一步说明：

> 重新开始会替换本轮全部本地合成演示数据，包括记录追溯。代码和独立 Knowledge 资料不受影响。

第二步确认：

> 我知道当前这轮合成演示记录会被替换。

最终按钮：

> 替换并开始新一轮

按钮执行期间显示：

> 正在准备新的合成演示，请勿重复操作……

失败时必须说明旧故事是否保留。现有原子替换合同支持的文案：

> 新一轮暂时无法开始，原来的演示记录没有被替换。请重试。

### 明确不采用

- 六张等权角色卡片；
- 9 个状态块铺满首页；
- QR、Observation、Task、Alert 等计数器作为第一屏；
- “M5-D”“Layer 3”等研发里程碑作为主标题；
- 大型 Dashboard 指标；
- 把 Knowledge 放进五步接力故事。

## 7.2 我的随访（`pages/1_patient_followup.py`）

### 页面职责

让患者在手机上确认“系统有没有准确理解我的话”，而不是确认诊断。

### 设计基准

- 主基准：`390×844`；
- 单列；
- 无角色导航；
- 首屏内能看到原话、系统记法、决定后果和至少两个完整操作按钮；
- 触控目标不小于 `44px`。

### 第一屏顺序

1. 标题：`我的随访`；
2. 原话：`“我今天拉肚子。”`；
3. 过渡：`我们记成了`；
4. 记录：`今天有腹泻`；
5. 主问题：`这和您想表达的是同一个意思吗？`；
6. 不可折叠的后果提示；
7. 三个等权决定；
8. 不可折叠的非诊断/未发送边界；
9. 两个次要入口：影响说明、本轮记录。

### 不可折叠的后果

> 如果这一轮的内容全部选择“不是这个意思”，本轮会结束，当前不能立即重新表述。

这句话必须放在按钮之前，不能只藏进“了解更多”。

### 三个等权按钮

```text
对，就是这个意思
我还不确定
不是这个意思
```

- 默认没有被预选的“推荐答案”；
- 三者同宽、同边框、同字号；
- 只有用户已选择的“我还不确定”使用轻量琥珀色状态；
- 不用绿色暗示接受是正确答案；
- 若一轮有多条候选，当前合同仍是整组决定，不宣称患者逐条签署。

### 患者端语言

使用：

- `您刚才说`；
- `我们记成了`；
- `这和您想表达的是同一个意思吗？`；
- `查看这一轮记录`。

禁止：

- 候选；
- 结构化临床事实；
- evidence；
- 人工门禁；
- 生成 Observation；
- 确认症状；
- 确认诊断。

### `candidate_unsure`

标题：

> 这段记录还没有确认。

说明：

> 您仍可以选择“对，就是这个意思”或“不是这个意思”。在您明确决定前，不会生成患者确认记录或护士任务。

主按钮仍可用，不转交护士或医生决定。

### 全部拒绝终态

标题：

> 这一轮到这里结束。

原因：

> 您选择了“不是这个意思”，系统没有形成患者确认记录。

已经产生：

- 患者原话；
- 本次决定记录。

没有产生：

- 患者确认记录；
- 护士核对任务；
- 医生速览；
- 任何临床评估或消息发送。

固定说明：

> 当前这一轮不能立即重新表述。如需演示新一轮，请由演示者明确重新开始。

### 患者确认后的回执

标题：

> 我们已经保存您的确认。

内容：

> 您确认的表述：今天有腹泻。下一步是由护士核对这条记录。

边界必须在回执上继续显示：

> 这不是诊断或风险判断，本演示不会发送消息。

### 完整问卷与旧技术路径

- 主比赛故事中不把完整 FHIR 问卷铺在候选确认下方；
- 不能用完整问卷按钮绕过 manual-review 门禁；
- 若旧技术演示仍需要完整问卷，放入 `其他填写方式` 的次要区域；
- Pathway、版本、会话 ID、模型 traces 和术语目录不进入患者第一、第二层。

### 急救提示

固定可见但不抢占主任务：

> 这里不是急救通道。如情况紧急，请立即联系当地急救服务或前往急诊，不要在这里等待回复。

## 7.3 护士工作台（`pages/2_nurse_risk_center.py`）

### 页面职责

让刚开始轮班的护士快速找到一条例行记录核对任务、理解来源并完成当前动作。

### 导航骨架

```text
护士工作台
├── 待处理
└── 已处理
```

不使用“风险中心”名称，因为当前 Task 不是风险 Alert。

### 队列规则

- 显示 `按提交时间排序`；
- 不按症状内容、颜色、逾期或页面位置形成事实上的风险排序；
- 每一行任务类型写 `例行记录核对`；
- 当前 Demo 只有一条时仍保留轻量列表—详情结构，但直接选中该任务；
- 多条时列表显示患者标识、提交时间、任务状态和一个中性摘要；
- 不显示严重程度、风险等级、红色紧急徽标或倒计时 SLA。

### 桌面第一屏

左侧约 30%：

- `待处理 / 已处理`；
- 排序说明；
- 任务行。

右侧约 70%：

1. 任务类型：`例行记录核对`；
2. 患者确认的表述：`今天有腹泻`；
3. 原话入口：`查看患者原话`；
4. 当前状态；
5. 当前唯一主动作；
6. 固定边界；
7. 先前动作和完整接力记录入口。

### 状态与动作映射

| Task 状态 | 主标题 | 主动作 | 次要动作 | 动作后反馈 |
|---|---|---|---|---|
| requested | 等待接手 | 接手这项核对 | 取消任务 | 已接手，下一步开始核对 |
| received | 已接手 | 开始核对 | 拒绝处理 / 取消任务 | 已开始核对 |
| in-progress | 正在核对 | 记录结果并生成沟通文字 | 取消任务 | 结果已保存，文字仍待人工核对 |
| completed + pending，尚无 pending 速览 | 沟通文字待核对 | 前往复诊速览 | 暂不提供文字确认主动作 | 医生明确生成 pending 速览；页面查看本身不写入 |
| completed + pending，已有 pending 速览 | 沟通文字待核对 | 确认文字已核对 | 无发送动作 | 文字已核对；模拟，未真实发送 |
| completed + ready | 核对已完成 | 前往复诊速览 | 无业务写入 | 本演示不会发送 |
| rejected/cancelled | 流程已停止 | 查看完整记录 | 无 | 不再提供业务动作 |

### 受控结果文案

使用：

```text
记录一致
需要补充说明
```

按钮：

> 记录结果并生成沟通文字

边界：

> 这里只记录核对结果，不形成诊断、风险等级或治疗建议。

### 沟通文字

标题：

> 待人工核对的沟通文字

就地标记：

> 模拟（未真实发送）

确认按钮：

> 确认文字已核对

按钮邻近说明：

> 这一步只确认文字可进入后续演示流程，不会发送给患者。

不能把底层 `ready-to-send` 直接翻译成“已发送”“发送准备完成”或“可以发送”。

### 拒绝和取消

进入确认区前必须显示后果：

> 这会停止后续业务动作；不会生成新的沟通文字或医生速览。已有记录仍会保留供追溯。

处理说明必填，提交后转只读终态。

### Alert 区域

- 不在护士主界面展示“已获批规则产生的 Alert 任务”空 Dashboard；
- 不展示 0 Alert、0 ClinicalRule 等三列指标；
- 若演示者需要证明边界，只在页面底部 `演示边界` 展开区显示：`临床警报未启用：0 条获批规则，0 条 Alert。`；
- 旧 Alert 兼容功能不能与 manual-review 队列混为一个工作列表。

## 7.4 复诊速览（`pages/3_doctor_summary.py`）

### 页面职责

让医生在复诊前快速分清：患者确认的事实、护理动作、尚未评估的部分。

### 第一屏三项事实

必须依次并列或纵向显示：

| 标签 | 内容示例 |
|---|---|
| 患者确认的表述 | 今天有腹泻 |
| 护理动作 | 护士已完成记录核对 |
| 当前边界 | 尚未提供临床评估 |

`尚未提供临床评估` 必须与摘要正文和医生决定区域相邻，不能只放成右上角小 badge，也不能折叠。

### 当前速览

示例：

> 患者表示今天有腹泻；护士已完成记录核对。尚未提供临床评估。

页面不能自动补充：

- 诊断；
- 风险等级；
- 严重程度结论；
- 用药建议；
- 处置建议；
- “医生还缺哪些问题”的自动推断。

### 来源展开

桌面端在正文右侧使用约 `180px` 的窄来源栏，或在对应事实行就地展开：

- `查看患者原话`；
- `查看护理动作详情`；
- `查看上一版措辞`；
- `查看完整接力记录`。

每次最多展开一个；展开后占整行，不让正文列宽来回跳动。

移动端来源放在对应内容下方，不使用横向滚动或全屏技术 Modal。

### Summary 空状态

无 completed Task：

> 还没有可生成速览的已完成记录核对。

有 completed Task、尚未生成：

> 已有一条完成的记录核对。生成速览是明确动作，查看或刷新页面不会自动生成。

按钮：

> 按当前记录生成速览

### 陈旧版本

标题：

> 这版速览基于较早记录。

说明：

> 患者确认、护理动作或沟通文字已经变化。旧版本继续保留，但不能冒充当前版本。

按钮：

> 按当前记录生成新版本

不自动覆盖旧版本，不并排显示红绿 diff。

### 医生措辞决定

三个等权选项：

```text
保留这版速览
调整速览措辞
不采用这版速览
```

邻近固定说明：

> 以上只调整速览的文字表达，不等于临床评估。

“不采用”旁说明：

> 不采用只影响这段速览文字，不改变患者确认的记录。

规则：

- 保留：记录对当前不可变 Summary 版本的决定；
- 调整：只选择并修改现有条目措辞，保留同一 evidence references；
- 不采用：产生 rejected 的不可变版本状态；
- 调整或不采用时说明必填；
- 不设计成协作文档、无限编辑器或临床签署界面；
- 不使用“批准、签署、定稿、审阅通过、写回病历”等词；
- `story_complete` 后只读，不再提交新决定。

### Knowledge 入口

Knowledge 不从患者事实旁做“相关证据”入口，也不携带患者上下文或自动预选主题。

如保留入口，只能位于页面底部独立资料区：

> 打开独立 Knowledge 资料库

> 只读，不携带患者上下文，不参与本轮状态。

## 8. Empty、Loading、Error 与终态体验

### 8.1 Empty 不是一种状态

| 场景 | 标题 | 说明 | 可用动作 |
|---|---|---|---|
| Demo 未开始 | 这次合成演示还没有开始 | 只准备未确认内容，不替角色作决定 | 演示者开始 |
| 患者无待确认内容 | 目前没有需要您确认的内容 | 不暗示系统正常或随访完成 | 查看本轮记录 |
| 护士无任务 | 目前没有待核对记录 | 不显示庆祝或“风险为零” | 查看已处理 |
| 医生无 Summary | 还没有可生成的复诊速览 | 说明缺少 completed Task 还是尚未明确生成 | 返回当前上游步骤 |
| 审计无事件 | 这一轮还没有留下流程记录 | 不补造默认时间线 | 返回演示导览 |
| Knowledge 无 Claim | 当前主题没有已登记的支持声明 | Knowledge 仍保持只读 | 查看来源/其他主题 |

### 8.2 Loading

只在真实等待期间使用，文案带主语和对象：

- `正在读取这一轮记录……`；
- `正在保存您的决定，请勿重复操作……`；
- `正在记录护士核对结果……`；
- `正在按当前来源生成速览……`。

规则：

- 禁用重复提交；
- 保持布局高度，避免按钮跳动；
- 超过合理时间后转可解释错误，不无限转圈；
- 不显示“AI 正在诊断/分析风险”。

### 8.3 Error

错误信息统一回答四件事：

1. 哪一步没有完成；
2. 之前的数据是否保留；
3. 系统没有继续做什么；
4. 用户现在能做什么。

示例：

> 这次决定没有保存，原来的记录没有变化，也没有创建护士任务。请重试；如果页面中的故事已经变化，请先刷新。

并发/旧故事冲突：

> 这轮演示已在另一个页面重新开始。当前页面不会继续写入，请刷新后再操作。

### 8.4 业务动作后的反馈

反馈写“发生了什么 + 下一步”，不只显示“成功”：

- `已保存您的确认。下一步由护士核对这条记录。`；
- `已接手。下一步开始核对。`；
- `核对结果已保存，沟通文字仍待人工确认。`；
- `文字已核对；本演示没有发送。`；
- `已按当前来源生成新一版速览。旧版本仍保留。`。

## 10. 响应式与无障碍

### 10.1 断点原则

| 宽度 | 主要布局 |
|---|---|
| `< 640px` | 单列；患者操作优先；来源就地展开；无横向表格 |
| `640–1023px` | 单列或 40/60 分栏；队列可折叠为顶部列表 |
| `≥ 1024px` | 护士列表—详情、医生正文—窄来源栏、审核动作表 |

### 10.2 患者移动端

- 按钮最小高度 `48px`；
- 相邻决定间距至少 `8px`；
- 长中文自然换行；
- 重要后果、边界和急救说明不被 sticky 区遮挡；
- 不把三种决定压成不可读的小按钮；窄屏可纵向等权排列；
- 不横向滚动；
- 返回入口与主决定保持视觉层级差异。

### 10.3 医护窄屏

- 护士队列先显示列表，再进入详情，不把桌面两栏硬缩；
- 医生三项事实纵向排列；
- 审核动作表改为带标签的记录行，而不是截断列；
- 技术 JSON 允许代码块内部滚动，但不能让整页横向滚动。

### 10.4 无障碍

- 所有关键状态同时使用文字和结构，不只依赖颜色；
- 展开控件提供明确名称和 `aria-expanded`；
- 键盘焦点可见，焦点顺序与视觉顺序一致；
- 触控目标至少 `44×44px`；
- 文本与背景满足 WCAG AA 对比度；
- 状态变化使用适当 live region，但不重复播报整页；
- loading 后焦点回到更新区域；
- 支持 `prefers-reduced-motion`；
- 页面标题和主标题能让屏幕阅读器区分角色空间。

## 12. Claude Opus 审查与 Codex 最终取舍

### 12.1 已采纳的关键审查

1. 患者全部拒绝会结束本轮，这个后果必须在提交前不可折叠；
2. 审核原因缺失时必须明确显示 `原因：未记录`，不能生成替代原因；
3. Mock 状态必须在具体外部动作旁显示；
4. 正常完成、业务停止和记录错误需要不同终态表达；
5. 护士队列必须声明按提交时间排序，不能暗中形成风险排序；
6. 患者确认回执仍需显示非诊断边界；
7. 医生的 `尚未提供临床评估` 必须邻近摘要与决定；
8. 重新开始必须是演示者专属、二次确认、明确替换范围；
9. 通用六项导航仍像比赛控制台，应改为角色化入口；
10. 演示者需要五步线性路径和一条负向路径，而不是六页磁贴。

### 12.2 未完全采纳

| Claude 建议 | Codex 判断 | 最终决定 |
|---|---|---|
| 删除 Knowledge | 完全删除会丢失现有独立只读能力；风险来自上下文混用而非页面存在本身 | 保留独立资料库，移出核心接力与患者上下文 |
| 把“患者确认行为数据”作为未来护城河 | 当前只有合成数据，真实数据还涉及同意、隐私、治理和医疗场景验证 | 不作为当前 moat，只能列为长期待验证假设 |
| 嵌入现有工作流优于独立产品 | 对降低采用阻力有战略价值，但当前尚未实现真实集成 | 作为路线假设，不写成现有能力 |

### 12.3 没有遗留的 Claude blocker

本规格已把会改变方案的体验 blocker 纳入。仍未解决的内容属于真实市场与实施验证问题，见第 16 节，不阻止先制作可回退原型。

## 13. 双模型拟人测试后的定稿规则

| 角色 | 原始误解风险 | A++ 修正 | 预期第一反应 |
|---|---|---|---|
| 患者 | 以为在确认诊断，或不知道拒绝全部会结束本轮 | 决定前显示后果；按钮改成日常语言；回执重复边界 | “系统在问有没有记对我的话” |
| 护士 | 把 manual Task 当成风险 Alert | 名称改为例行记录核对；按提交时间排序；移除 Alert 指标 | “这是要接手的一条记录核对” |
| 医生 | 把 Summary 当作系统临床结论 | 第一屏固定分开事实、护理动作、尚未评估 | “这是复诊前资料整理，不是诊断” |
| 审核者 | 先看到英文事件和 JSON，不知道为什么停止 | 结论—原因—已产生—未产生—动作表—技术详情 | “我能先解释结果，再查底层记录” |

自然语言验收不只检查名词，还要检查整句：

- 是否有明确主语；
- 是否说明动作对象；
- 是否说清动作后果；
- 是否给出下一步；
- 是否会暗示诊断、风险、发送或审批；
- 按钮是否像真实用户会执行的动作。

归纳后的五条原则：

1. 导航围绕角色当前工作，不围绕系统所有能力；
2. 用户状态语言与内部枚举分开；
3. 第一屏给唯一下一步，完整历史按需展开；
4. 异常状态说明“为什么、保留了什么、没有继续什么”；
5. 新工作台必须证明替代了什么工作，否则会变成额外负担。

## 15. 投资者与战略咨询视角的校正

### 15.1 当前可讲的产品楔子

推荐先验证：

> **非紧急、计划内的诊后随访或复诊前资料准备。**

原因：

- 与当前“患者表达—确认—人工核对—复诊速览—追溯”能力一致；
- 不需要虚构急症分诊、风险 Alert 或真实发送；
- 能把核心亮点集中在跨角色信息失真和重复澄清问题上。

这仍是战略假设，尚未经过真实机构、科室和用户研究验证。

### 15.2 首要角色与经济买方假设

当前产品角色优先级：

1. 患者：内容的原始参与者与确认者；
2. 护士：潜在日常操作角色，也是采用阻力最高的角色；
3. 医生：高价值、低频快速消费角色；
4. 审核者：可信度和异常解释角色；
5. 演示者：销售与产品验证的元角色。

工作假设是潜在买方更可能接近照护运营或具体随访工作流负责人，但目前没有足够证据确定签约人、预算归属和采购路径。不得把“医院/医护”笼统写成已确定买方。

### 15.3 最大采用风险

> 如果 ContinuCare 只是增加一个护士必须额外查看的队列，而没有替代电话、消息整理、手工复制或重复澄清，它会增加工作量。

因此后续真实产品路线优先级应是：

1. 先验证能否嵌入或贴近现有工作流；
2. 先验证入站记录和上下文带入，而不是先做真实发送；
3. 明确替代哪一步现有工作；
4. 再考虑真实外部集成。

这不是本次 UI 实施范围。

### 15.4 当前不能讲的商业主张

- 不声称节省护士时间；
- 不声称降低临床风险；
- 不声称提高诊断准确率；
- 不声称已经集成医院系统；
- 不声称已进入临床试点；
- 不把合成患者确认数据称为数据护城河；
- 不把“可追溯设计”直接称为不可复制技术壁垒。

### 15.5 后续应验证的价值指标

不在 Demo 中伪造数据，只定义未来验证指标：

- 一次随访需要多少轮人工澄清；
- 护士从打开任务到做出正确动作的时间；
- 医生区分患者事实、护理动作和未评估边界的时间；
- 审核者解释异常终态的时间；
- 用户误以为系统已诊断、分级或发送的比例；
- 新工作流实际替代的旧步骤数量；
- 净新增操作时间，而不是只测单页完成时间。

### 15.6 当前诚实叙事

推荐对投资者或设计合作方这样讲：

> ContinuCare 正在验证一个问题：患者说的话能否在随访、护士核对和复诊准备之间保持原意、来源和边界，同时减少重复解释。现在展示的是合成数据产品原型；我们希望先和设计合作方验证工作流，再决定真实集成和临床验证路线。

## 17. 验收标准

### 17.1 产品理解

- 患者 5 秒内能说出“系统在问有没有记对我的话”；
- 护士 5 秒内能找到当前唯一待办，并明确这不是风险警报；
- 医生第一屏能分清患者事实、护理动作和未评估边界；
- 审核者不打开 JSON 就能解释为什么完成或停止；
- 演示者不需要口头翻译 M5、FHIR、candidate 或 ready-to-send；
- 任一角色都能在一次展开内找到所需来源或完整记录入口。

- 页面不存在“诊断、风险等级、治疗建议、已发送、联系医生、真实集成成功”等误导；

- 全部拒绝后不提供同轮立即重说；
- Task 异常终态无业务动作；
- story_complete 不等于临床完成；
- Knowledge 不参与故事；
- Mock 状态就地出现；

- 桌面 `1280×720` 首屏不被技术说明淹没；

- 状态不只靠颜色；
